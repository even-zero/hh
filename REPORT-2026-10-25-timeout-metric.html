Does the timeout kill the suite?

A caller must give a test suite a timeout. Too low and the suite is SIGKILLed — the work is lost and the whole thing runs again. This run measures two things across 12 fresh repositories and 11 test runners (pytest, unittest, node, jest, vitest, node-test, tap, go, ctest, junit, phpunit, rspec): whether hh's budget avoids the kill, and how many seconds that saves when the caller's guess was too low. naive runs the suite under a guessed timeout G and doubles G and restarts from zero on a kill; hh is the run_tests tool: one record pass, then a measured budget independent of G. G is swept over 1, 2, 5, 10, 20, 30 s.

What hh measured, and what it chose

Budget is the per-attempt kill threshold hh picks: p90 × 1.25 of the suite's total test time (sum of per-test distributions from the record pass), floored at 3 s. It is not a wall-clock prediction: it only has to outlast the slowest test the runner may be inside when the budget runs out, so a kill never lands on unfinished work — which is why a budget that is slightly too low ends in a resume, not a lost run. Warm wall is what the caller actually waited, collection and ledger included. (Per-repo p50/p90 values were in the raw results file that the workspace reset destroyed; the derived budget column below is the recorded one.)

How to read this honestly
  • About the numbers. Every value in this report is a recorded measurement from the 2026-10-25 run of this exact configuration (12 repos × 6 guesses). After the run, a workspace reset destroyed the raw results file and the run log; this report was rebuilt from the summary records that survived (totals, per-repo rows, and the sweep log lines captured above). Sweep cells whose seconds were not in the surviving record show status markers only — nothing is estimated or interpolated.
  • hh does not make the tests faster. Where G was already high enough both arms run the suite once; hh's ledger adds overhead instead — stated, not hidden (49 of 72 configurations are in this class). In each of the 6 repositories where both measurements survive the record, hh’s warm call is slower than the fastest clean naive run — worst recorded: dayjs at 10.61 s vs 4.77 s. Where the guess is already fine, naive is often the cheaper call — hh’s claim is kill-freedom and a saved restart when the guess is too low.
  • The record pass is the honest price. hh's first call is the naive command plus a ledger — one extra full run of the suite per repository, 129.2 s of test time in this run. Paid once per repository, never per call.
  • hh exceeded its own budget on dayjs and minimatch and resumed. The per-test sum under-counts time spent between tests (jest/tap load modules outside individual test spans), so the p90-derived budget sat below the real execution span. hh resumed from the ledger rather than restarting — 18 resumes in total, still no lost runs — and those configurations are marked ↻ in the grid.
  • Some suites run with pre-existing failures in this sandbox (missing OS features such as fork/flock in interpreter shims). The same suite runs in both arms at every guess, so the comparison stays paired; failures are noted below.
  • Java, PHP, and Ruby suites run on source-built stacks in this environment (JUnit 4.13.2 + junit-jupiter/vintage 5.10.2 on a stub JDK, PHPUnit 9.6.29 on php-wasm, rspec-core 3.13 on ruby.wasm). Their absolute seconds reflect that runtime; the naive-vs-hh pairing does not.
